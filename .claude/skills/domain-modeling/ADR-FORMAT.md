# ADR Format

> Адаптировано под этот проект: путь, нумерация и язык отличаются от апстрима
> `mattpocock/skills`. Полная конвенция и индекс — `memory-bank/decisions/README.md`,
> он источник истины; этот файл — выжимка для скилла.

ADR живут в `memory-bank/decisions/` (не в `docs/adr/`) и называются `ADR-NNNN-kebab-slug.md`
с четырёхзначным номером. Каталог уже существует — создавать не нужно.

Язык новых ADR — **русский**. Уже написанные по-английски не переводим.

## Template

```md
---
type: adr
number: "NNNN"
title: Короткое название решения
date: YYYY-MM-DD
status: accepted
tags: [architecture, ...]
---

# ADR-NNNN: Короткое название решения

{1–3 предложения: какой был контекст, что решили и почему.}
```

Этого достаточно. ADR может быть одним абзацем — ценность в фиксации того, *что* решение
принято и *почему*, а не в заполнении разделов. В каталоге есть старые ADR на 200+ строк:
это исторический перекос, не образец для новых.

## Optional sections

Добавляй только когда они реально что-то дают. Большинству ADR они не нужны.

- **Альтернативы** — когда отклонённые варианты стоит помнить (иначе их предложат снова).
- **Последствия** — когда есть неочевидные downstream-эффекты.
- `status` в frontmatter меняется на `deprecated` или `superseded by ADR-NNNN`,
  когда решение пересматривают.

## Numbering

Просканируй `memory-bank/decisions/` на максимальный номер и увеличь на один.
Номер — идентификатор, не хронология: не переставляй номера существующих ADR.
Номерное пространство принадлежит только `memory-bank/decisions/`; в
`memory-bank/_archive/decisions/` лежат записи, снятые с серии и потерявшие номер.

## When to offer an ADR

Все три условия должны быть верны:

1. **Трудно обратить** — сменить решение потом дорого.
2. **Неочевидно без контекста** — будущий читатель кода спросит «почему так?».
3. **Был реальный размен** — существовали настоящие альтернативы, выбрали одну по причинам.

Легко обратимо → не пиши, просто обратишь. Не удивляет → никто не спросит. Альтернатив не было
→ фиксировать нечего, кроме «сделали очевидное».

**Конвенция кодирования — не ADR.** Правила стиля, организации утилит, именования файлов идут в
`memory-bank/code-standards/`. Как что-то делать пошагово — в `memory-bank/runbooks/`.
Чему научились на граблях — в `memory-bank/lessons/`. Что сломано — в `memory-bank/known-issues/`.

### Что квалифицируется (с примерами из этого проекта)

- **Форма архитектуры.** Слои `domain/` / `projections/` / `general_ledger/` / `usecases/`,
  зеркалирование структуры между тремя крейтами (VSA).
- **Необратимое в данных.** Схема БД и миграции `migrations/NNNN_*.sql` — append-only,
  применяются на старте бэкенда. Маппинг проводок Главной книги: изменение требует
  репоста документов через `u508`.
- **Границы и владение.** Какой слой учёта (`fact` / `fina` / `ybuh`) отвечает за какую сверку;
  что читает `dsNN`, а что `dvNN` (см. ADR-0010).
- **Технологии с lock-in.** SQLite/SeaORM, Leptos/WASM, Thaw UI, QuickJS для плагинов —
  не каждая библиотека, а те, замена которых займёт кварталы.
- **Осознанное отклонение от очевидного пути.** Например: логи задач пишутся в JSON-файлы,
  а не в БД (ADR-0003) — иначе следующий инженер «починит» то, что сделано намеренно.
- **Ограничения, невидимые в коде.** Лимиты и особенности API маркетплейсов (WB/Ozon/YM/1С),
  требования по времени ответа, ограничения SQL-гарда для плагинов.
- **Отклонённые альтернативы, когда отклонение неочевидно.**
