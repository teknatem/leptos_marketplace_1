# Quality checks

`quality_checks` — единый источник исполняемых правил качества данных. Им пользуются UI,
LLM-инструменты и планировщик; навыки не должны хранить копии диагностического SQL.

## Модель правила

Одна проверка отвечает за одну понятную цель и небольшой набор однотипных инвариантов над
одной бизнес-популяцией. В карточке обязательно объясняются популяция, условие нарушения и
границы проверки. Разные бизнес-процессы или разные способы исправления оформляются отдельными
проверками, даже если технически читают одну проекцию.

MJS-пакет состоит из `check.json`, `check.mjs` и необязательной `schema.json`. Код получает
только заявленные `db:read:<table>` и возвращает `metrics`, `violations`, `breakdowns`, `sources`.
Rust валидирует результат, ограничивает время/память/строки/размер и сохраняет запуск с digest
определения. Сеть, файлы и запись в БД недоступны. Исправляющие операции остаются Rust-командами.

## Для человека

Страница «Контроль качества данных» показывает карточки правил и последний запуск текущей
версии. Название открывает детали. Результат старого digest не выдаётся за результат изменённого
правила. Ручной запуск и планировщик пишут в одну историю.

## Для LLM и распределение ответственности

Skill `quality-monitoring` доступен всем специальностям: обзор каталога, чтение свежего результата
и точечный запуск. Skill `quality-check-authoring` доступен `plugin_admin`: шаблон, чтение bundle,
валидация и атомарный upsert внешнего пакета.

`business_analyst` владеет постановкой: цель, популяция, инвариант, исключения, период, разрезы и
приёмочные примеры. `plugin_admin` владеет исполняемой реализацией, SQL/capabilities, sandbox и
публикацией. Это предотвращает незаметное изменение бизнес-смысла и не требует от аналитика
поддерживать runtime-код. После явного подтверждения пользователя `quality_check_upsert` заменяет
пакет и выполняет reload; при ошибке файлы откатываются.
